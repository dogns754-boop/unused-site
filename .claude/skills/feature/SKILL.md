# 기능 하나 구현

대상: `$ARGUMENTS`

## 0. 준비
- `projects/<프로젝트>/PLAN.md` 를 읽는다. 기능 설명이 없으면 **첫 번째 미완료 `- [ ]` 항목**을 고른다.
- 지정한 기능이 PLAN.md 에 없으면 먼저 체크리스트에 추가한다 (범위가 크면 쪼개자고 제안).
- 관련 코드와 테스트를 읽고, 무엇을 어떻게 바꿀지 **3~5줄 계획**을 사용자에게 보여준 뒤 진행한다.
  변경이 아주 작으면 계획을 보여주고 바로 진행해도 된다.

## 1. 테스트 먼저 (Red)
- 기능의 기대 동작을 테스트로 쓴다. 정상 경우 + 경계/오류 경우 최소 1개.
- `scripts/check.sh <프로젝트>` 로 **새 테스트가 실패하는 것**을 확인한다.

## 2. 구현 (Green)
- 테스트를 통과시키는 가장 단순한 코드를 쓴다.
- 입출력(CLI 파싱, DOM, 파일)과 순수 로직을 분리해 로직을 테스트하기 쉽게 둔다.
- `scripts/check.sh <프로젝트>` 통과까지 반복한다.

## 3. 정리 (Refactor)
- 중복·이름·구조를 다듬는다. 다듬은 뒤 다시 check 통과를 확인한다.
- 실제로 한 번 실행해 본다 (README 의 실행 방법대로).

## 4. 기록과 커밋
- PLAN.md: 해당 항목 `[x]`. 상태가 `🌱 기획` 이면 `🔨 개발 중` 으로 (PROJECTS.md 도 같이).
  모든 MVP 항목이 끝나면 사용자에게 `✅ 완성` 으로 바꿀지 묻는다.
- CHANGELOG.md `[Unreleased]` → `### 추가` 에 한 줄.
- 사용법이 바뀌었으면 README.md 갱신.
- 커밋: `[<프로젝트>] feat: <요약>`

## 5. 보고
- 무엇을 만들었고 어떻게 써보는지 2~3줄, 다음 미완료 항목을 알려준다.
- 이 기능을 하다 발견한 **범위 밖의 할 일**은 고치지 말고 PLAN.md `3. 나중에` 에 적는다.
